# Ingest 阶段闸门清单

执行前核对运行的 execution_profile：新 core/deferred 可走 consolidated-v1，existing 与历史运行保留原合同。共同内容闸门继续适用，具体执行与审核者路由见[便携执行说明](../../protocols/PORTABLE_EXECUTION.md)，不混用不同 profile 的审核证据。

> **用途**：固定统一 Ingest 流水线的阶段包，以及标准和自动两种审核模式。
> **适用**：所有 URL / IMA / Clippings / 多 URL / 补审式 Ingest；自动消化仅适用于协议规定的 direct 或 managed-isolated 单批任务。
> **协议归属**：`system/protocols/INGEST_PROTOCOL.md` 是三阶段行为与状态转换 SSOT；本文只固定各阶段输出闸门。

## 0. 授权粒度

标准消化在评分、raw、归属规划和写入闭合四个闸门审核；旧称快速映射标准、仅精简展示，同样保存运行单、包、收据与反查索引。普通 start 默认 interactive。显式自动才 deferred，将中间人工介入后置到最终；同一质量线不降低，来源、raw 与 Wiki 前的可恢复边界必须可验证，真实授权/证据阻断即时报告。新 run schema 8 使用 package-data v2 / renderer v2；历史 schema 5/6/7 只按旧格式读取，不重渲染旧审批。可选精确语义复核与现行确定性包共存，不因 precision 回退创建 schema 5。

schema 8 每份 Raw 必须通过 `raw-quality.mjs` v2 全文双向独立复核，缺 host-observed 调用记录不得通过；这与可选的整阶段精确审核不同。

启用 precision/enforced 时，评分与阶段一在 check-stage1 前、阶段二在 check-stage2 前、阶段三在 check-stage3 前须有相应 valid_pass；最终审核再复验来源版本。普通同上下文回读不得冒充不同上下文的独立复核。
- 评分闸门通过：只授权写 raw 消化稿，或写 skipped；不授权 wiki 写入。Clippings 来源在此授权后、任何 raw / skipped 写入前，须统一重命名本批所有已确认终态材料（含 🔴 跳过项）并输出清单。
- 阶段一审核通过：只授权进入阶段二归属规划；不授权 wiki 写入。
- 阶段二审核通过：才授权阶段三 wiki 写入、raw-list、index、维护链。
- 用户说"按推荐执行 / 按你推荐方式 / 可以"时，只默认确认**当前闸门**；除非用户明确说"阶段二三也一起做"。

标准消化必须先以 `review_policy=interactive` 创建运行清单。每个 §5.1～5.4 包先保存到该批目录并执行 `record-package`。评分、Stage1、Stage2 给出包 SHA-256，批准后用 `approve-gate -Gate <gate> -ApprovedHash <sha256>` 推进；Stage1 后执行 check-stage1 建立 checkpoint。Stage3 内容和维护通过后，两模式均由 render-final-review / verify-final-review 展示当前最终版本，用户批准后 finish，不用 approve-gate stage3 直接结束。包在批准后发生变化时，旧批准立即失效，必须重新展示并重新批准。

标准与自动消化的来源与 raw 使用 `record-artifact` 登记：每个输入必须用 `-InputItem`，或推荐的零基 `-InputItemIndex`，精确关联其 `input / ingested|skipped` 映射；原始标题含弯引号、管道或其他易被 wrapper 二次解析的字符时，必须用 `-InputItemIndex`，不让 `.cmd` 承载原文。有 `ingested` 输入时至少有一条 `raw / ingested` 映射。登记顺序固定为：输入映射 → raw artifact → 对应 `record-content-audit` 收据；收据依赖 raw 已存在，禁止倒序调用。自动模式须在阶段一 checkpoint 前登记完成，`check-stage1` 会拒绝缺失或错配映射；标准模式也在闭合时复核。启用语义审核时，每个 request/receipt 也必须留在同批目录，且 stale/revise/escalate 不能绕过上述门。两模式都在最终精确版本批准后由 `finish` 闭合并更新 `system/maintenance/ingest-runs/index.json`。

## 1. 阶段一输出包（写 raw 后硬停）

必须一次性输出：

- raw 文件链接（逐篇），以及每篇 `content_summary`：具体主题、关键论证、数据/边界和未转录媒体
- 编写规则自检表（格式完整性 / 来源与 domains / 清晰标题和连贯正文）
- `内容审核收据摘要`：全部逐单元审核通过并登记后，由 `render-stage1-audit-summary` 生成，原样写入并保留 `CONTENT_AUDIT_SUMMARY_V1`；禁止手填或改写
- `写作骨架逐篇证据`：每份 raw 一行记录“原文模块→核心命题→载体→原文推导→例证/数据”，载体按语义选择而不设表格配额；以 `WRITING_SKELETON_V1` 标记
- `风格与来源边界抽检`：列出当前样板基线，至少抽检 `min(2, 本批 raw 数)` 篇，所有风格脚本异常或来源边界存疑项必须额外纳入；以 `STYLE_BOUNDARY_SPOTCHECK_V1` 标记
- 完整 source→Raw、Raw→source 及跨章复核收据；比例仅为兼容诊断，不作为写作目标
- 批注摘要（亮点 N / 可延伸 N / 存疑 N / 冗余 N；没有则写 0）
- 需用户审核的问题（内容准确性、批注是否保留/删除/改写）

**禁止**：阶段一审核通过前，修改 wiki / index / raw-list / domains / CHANGELOG。

**完整审核资格**：仅当“全文映射审核”“结构检查”“写作风格检查”均为 ✅ 才可写“可审核”。字段、标题、位置标注、行数或任一静态脚本通过都不能替代逐单元收据；缺 source manifest、任一来源单元未裁决或失败、收据摘要与控制器生成值不一致、未预读当前样板、正文丢失推理联系或将完整解释压成结论提纲，均必须写“❌ 不可审核”。

**强制脚本门禁**：标准和自动模式的 `check-stage1` 会对全部登记 raw 重跑样式检查，要求每份 ingested raw 唯一绑定 `stage1` 模式、0 个失败单元的全文映射审核收据，逐篇骨架行与 raw 身份一致，并把阶段一摘要与控制器重新生成值做精确比较。`check-raw-depth.ps1` 只保留为旧批次矩阵兼容复验工具，不参与新 Stage 1。

**回读判定（强制）**：source manifest 逐单元裁决与收据是范围完整性的唯一事实源；人工抽检只负责风格和来源边界。逐单元失败数为 0 是进入审核的必要门禁；裁决的语义真实性仍需实际 source→raw 回读，工具不能独立证明正文充分。压缩比异常只触发回读，不能替代结论。确认遗漏时默认只补写或扩写；若逐句对照确认旧文含原文不支持的归属、案例或结论，只允许最小原位校正并在审核记录留痕，禁止整体重写。熔断或历史补审使用运行目录的 `depth-remediation.md` 与 `check-depth-remediation.ps1`；其中任一“需扩写/存疑”在 `recover-fused` 后强制退回阶段一。补写改变已完成批次的 Stage 1 内容时，必须由 `rebase-stage1-baseline` 记录并重建合法 diff 基线，不得将旧 Stage 3 范围误算进 Stage 1。

**压缩比异常回查**：历史包保留正文 N/M/P% 诊断字段，但比例不构成独立门禁：
- 比例明显偏离常见区间 → 回读全文 manifest，核查是否漏掉独立内容单元、论证链、定义、案例、引用或数据；审核包记录回查范围与结论
- **记录粒度**：触发压缩比异常回查时，审核包逐 raw 一行记录回读证据；正常批次（无异常触发）由控制器在 `record-package -Package stage1` 时生成一行批次级汇总即可，不要求逐 raw 展开。标准与自动模式的控制器在写包时自动判断并选择记录粒度。
- 未发现遗漏且写作仍符合样板 → ✅ 可审核；不得为比例拆句、重复解释或增加无增量表格
- 发现遗漏 → ❌ 不可审核，按遗漏内容补写
- 任一逐单元审核失败 → 仍为不可审核；比例正常不能替代全文审核

## 2. 阶段二输出包（归属规划后硬停）

必须一次性输出：

- 领域覆盖反思：是否需新增/调整域
- Wiki 归属建议：更新哪个现有 wiki / 是否新建 / 是否孤立
- 批注消费路径：逐条说明目标 wiki、目标段落、处理方式
- 未消费风险：哪些内容可能无法被目标 wiki 吸收
- 行数预估原则：只作为写后拆分信号，不作为压缩内容或降低消化深度的理由。

**禁止**：阶段二审核通过前，修改 wiki / raw 批注 / raw-list / index / domains。

---

## 3. 阶段三输出包（写入维护后收尾）

必须一次性输出：

- Wiki 写入确认
- 批注消费确认
- 未消费内容检查结果
- 维护同步确认（raw-list / index / CHANGELOG / domains / NOW）

阶段三完成后，标准与自动模式先记录 Stage 3 包与维护收据、验证回测，再渲染/验证最终审核包并显示其 SHA-256。每个回测锚点必须同时具备 A 类评分结果与已闭合的内容回测收据；内容报告覆盖“批量抽查→易漏项矩阵→raw 修复与 Wiki 影响复核→全库筛选→回读→异常处理→总结”，并逐篇锁定计划时 raw 哈希。若 raw 哈希变化，报告必须记录修复证据、既有 Wiki 复核与处置；默认未拆分，拆分必须引用明确授权。两模式只在用户批准当前最终报告 hash、finish 验证引用版本后标记 completed 并进入收尾；内容提交不代替人工批准。

## 4. 补审场景

如果发现 AI 已越过闸门：

1. 停止继续消化新材料。
2. 先修流程规则。
3. 对已写 raw 重新输出阶段一审核包。
4. 将已写 wiki 视为"待确认写入"：用户可选择保留、重写或回滚。

## 6. 最终审核闸门（两模式共用，自动含回滚审计）

### 6.1 自动路径附加断言

- 用户有显式自动消化触发语；启动证据必须二选一：direct 的 `mode=direct/direct_start_allowed=true`，或 managed 的 task active、repository=knowledge、mode=isolated、owned worktree 与 execution_path/base 精确匹配。
- 批次建议为 2～3 个最终 raw、常规不超过 4 个；超出时必须先说明拆分理由或继续风险，但不是硬限制。多个命名批次若各自过小，可在阶段一回滚点前通过 `merge-pending` 合并为一个自动运行单；合并总输入≤6，必须保存原批次标签，已登记证据或已有 checkpoint 时不得合并。状态从 `inactive` 进入 `running`，阶段三后为 `awaiting_final_review`。
- §5.1～5.4 四个包均完整保留，且各自满足原模板的模型建议行规则；包必须链接 raw / 原始证据并呈现可审阅的实质内容，完整矩阵与日志按需展开。
- 阶段三包必须保留模板中的精确字面标记 `验证：`；`### 验证` 等标题不能替代该合同字段。登记前先运行 `record-package -Package stage3`，失败时停在本阶段修复，不生成最终审核包。
- 自动门禁日志逐项列出"判定 / 依据 / 是否修复 / 结果"，没有把用户审核后置误写成免审核。
- 阶段一 checkpoint 与阶段三内容 commit 均存在，范围分别符合协议；direct 的最终退出 commit 尚未创建；managed 的单结果 close 尚未执行。
- `ingest-control.ps1 check-backtests` 已确认全部跨越锚点各有唯一评分收据和通过的内容回测收据；`run-ingest-maintenance.ps1` 收据为 `passed` 且没有失败检查。
- 所有熔断项均已检查且当前未命中。任一命中时不得发送"最终审核包"，改为即时熔断报告。
- **最终审核包输出完整性止回阀**：若本轮启动了自动审核（`status` 从 `inactive`→`running`），则 §6.2 的五份证据对应的内容（评分包/阶段一闭合包/阶段二规划/阶段三闭合包/自动门禁与回滚审计表）**缺一不可**。不含门禁审计内容的"审核包"不是合法的自动审核最终输出；不得在未覆盖全部内容的情况下进入用户审核→退出→收尾。五段必须给出各自的完整证据链接和 SHA-256，不能因前序对话已出现而省略。（历史反例：连续批准不能省略门禁证据）
- §6.2 不再允许 AI 手工拼包：必须由 `ingest-control.ps1 render-final-review` 从五份已记录证据生成，再以 `verify-final-review` 验证分包及引用内容版本、现行内容段落和最终包哈希。最终审核通过只对该 SHA-256 生效。

### 6.2 最终统一输出结构

现行 renderer 从封存语义、真实 raw、Wiki diff 与分包生成报告；下表是内容合同，不允许 Agent 手写一份与渲染器平行的结果。五份已记录分包仍保留完整证据链接和 SHA-256，但只列链接不构成审核交付。

| 报告内容 | 读者必须能看到什么 |
|---|---|
| 评分与取舍 | 每份输入（包括 skipped）的分数、理由、历史差异、条件消化方式 |
| 新增 raw | 每份 raw 的主题、关键内容、论证/数字/媒体边界、直达全文；不是文件名和计数 |
| Wiki 增量 | 每页实际章节、新增/修改含义或精确 diff；来源、条件、冲突和未吸收去向 |
| 拆分 | 无拆分明确无；已拆分展示原因、拆前后映射、内容和来源去向、导航与旧锚点结果；提案不写成已执行 |
| 回测与维护 | 触发依据、范围、执行结果、修复与遗留；not_triggered/not_run/failed/passed/reused 分开，复用须附有效版本 |
| 实际例外与决定 | 未转录媒体、无法吸收或未解决问题及需要用户做的具体决定；无异常不堆空表 |
| 状态和恢复 | 批次、当前状态、Stage 1/Stage 3 恢复点、批准 hash 与引用内容版本清单 |

标准模式最终汇总复用已审结果并突出后续变化；自动模式在此让用户一次审完相同范围。底层全文/详细日志可展开，避免整批重复复制；摘要不能掩盖遗漏、冲突、未读或未执行。

发送前执行 `render-final-review` 与 `verify-final-review`，给出 `审核对象 SHA-256：<验证输出>`。批准绑定最终包及所引用的实际内容版本；包 Markdown 未变但 source/raw/Wiki 变化也须拒绝旧批准。内容执行完成不等于批准或 finish；自动保持 awaiting_final_review，获当前精确版本批准后才退出本批。

## 8. 现行版本依赖与局部重做

`seal-package-section` 绑定输入、raw、保真收据和本阶段规则版本。评分、raw审核和归属规划引用的既有 Wiki 会保留观察时的完整副本，写入前核对原页版本；合法融合后保留此前依据，最终报告再绑定融合后的真实 Wiki 和完整差异。相关正文、规则、已删除页面重建或新增未申报 Wiki 都会使旧最终审核失效。

发现后续阶段问题，用 `reopen-package-section -Package <scoring|stage1|stage2|stage3|gate_audit> -Reason <具体原因>` 归档旧运行单、包和审核版本，并清除受影响阶段及下游结果。未受影响的上游审批保留。该动作只重开流程，不擅自回滚知识正文；需要撤回写入时，先记录当前路径和差异，核对本批 Stage1 checkpoint 及 owner，再只恢复本批明确受影响的路径。修复、重做对应内容和维护后重新生成最终报告，旧哈希不能批准新内容。历史已完成批次不重开或改写。
