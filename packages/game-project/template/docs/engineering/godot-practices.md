# Godot 工程指导 · v0.1

适用：小团队正式开发，按功能渐进扩展。此文件给默认原则和检查标准，不预装玩法、存档、联网或框架；项目在 architecture-baseline/决定记录中说明必要例外。模板初始化仍只留配置指定的空工程位置，由 Godot 生成，目录名不固定为 godot。

## 1. 组织与所有权

文件按功能聚合，功能的 scene、script、私有资源尽量相邻。共享资源只有多个真实消费者时才提取，不先造 service 层或万能 utils。按文件扩展名建立全局 scripts/scenes/textures 三大筐不是默认。

可参考的引擎目录（按需要创建，不能把本例直接视为必建目录）：

```text
<configured_engine>/
  project.godot
  app/              # 启动、顶层场景切换、依赖装配
  features/         # battle/menu 等，每个功能就近拥有场景与脚本
  shared/           # 已证实跨功能复用的 UI/基础能力
  assets/           # 共用与外部受管资源；私有资源也可就近放功能内
  addons/           # 经审计的插件，区分编辑器与运行依赖
  tests/            # 可在引擎里运行的测试，实际发行包排除
```

工作空间 maintenance、docs、demo 和原始美术不塞进运行工程。每个受维护目录有 README，路由到直接下级；不能让所有文件夹列全项目树。不要为符合示例重命名已有稳定功能。

## 2. 场景组合而不是隐藏的整屏脚本

- Main 只装配依赖和切场景。复杂 HUD、对话框、战场、单位显示分别可在编辑器打开；固定 UI 用 Control/Container 和 Theme。动态单位可按数据实例化，规则驱动网格可保留自绘；不强迫每格一个节点。
- 节点的父子关系表达生命周期：删父级应合理地结束子级。输入监听、Tween、信号、临时资源跟随所属场景释放；切场景/取消回放必须有清理路径。
- 子场景不通过 ../../ 或全树搜索猜外部结构；由装配者传依赖，子场景发已发生事件，父级调用明确方法。局部 %Name 可以用，但不要跨场景依赖别人的内部节点名。
- 编辑器可调颜色、Texture、布局、动画参数与规则配置分开。已采用资产通过样式/资源定义替换，不逐英雄加硬编码绘图分支。

## 3. 规则、会话与表现

回合策略默认链路：输入意图 → 控制器校验 → 规则产生新状态/事件 → 只读表现回放。状态的写 owner 唯一；预览在副本上运行，不污染正式状态。动画结束不决定伤害、随机或胜负。

物理驱动游戏可以由引擎物理拥有相应事实；应明写边界，不强迫所有品类复制本项目的纯数据战斗实现。

每个模块最少说明：输入、输出、状态 owner、依赖、可观察副作用、生命周期、测试入口。优先明确公共 API 的类型；外部 Dictionary 在边界验证，避免跨模块直接改嵌套字段。不要仅为风格将稳定数据契约全量替换。

## 4. 数据与服务

- 静态定义、局内可变实例、持久化数据分开。编辑器主导的图像/音频/角色展示定义适合 typed Resource；跨工具对照和表格内容可以继续 JSON。相同事实只能有一个权威来源，导出/加载适配不变成第二份手写 SSOT。
- Resource 默认视为共享定义；修改实例数据前显式复制或使用独立 State，注意嵌套对象共享。存档须有 schema/migration、损坏处理和恢复路径，但没有存档切片就不预建。
- Autoload 只用于必须跨场景存活且真正全局的少量服务。不得把当场战斗、所有 UI 或消息转发塞进全局单例。每个 Autoload 说明职责、寿命、重置和发行资格；MCP 不进发行。

## 5. 工程约定与可维护性

新文件/目录默认 snake_case，类和节点 PascalCase（第三方原名/C# 例外）。提交 project.godot、源资源及导入设置 sidecar，保留 Godot 生成的 .uid；忽略 .godot 缓存，不能把 .uid 当缓存删掉。移动/改名优先在编辑器操作并复查 uid/path 引用；不要为了本次指南重写用户未提交配置。

第三方插件单独审核许可、版本、自动加载、依赖和导出；外部资源用来源收据。生成原图/参考/提示和运行精选分开，接入由 GamePresentation 的当前流程拥有；模型/服务不成为游戏运行依赖。

## 6. 每个改动的验收与渐进迁移

从 maintenance 进入：列影响模块 → 核对 owner/依赖 → 确定最小切片 → 实施 → 验证 → 独立提交恢复点。不要在一次切片同时换规则、目录、美术和输入体系。

必须按影响选择：纯规则测试；场景单独实例化/关闭；缺必要资源显式报错；UI 导航/退出与最小窗口；取消/跳过/重入；固定状态截图和密集盘面；实际包启动/资源/调试桥排除。无关输入未变可以复用旧证据，不能把新目录存在当架构测试通过。

重构触发看实际问题：跨模块改一次牵连多处、UI 无法在编辑器调整、共享定义被误改、重入/释放失效、资源替换必须改规则等。行数是提醒，不作为强制拆分门。每次迁移保留旧行为对照与文件映射，再删旧路径；不建立永久双运行实现。

## 依据与边界

[Godot 场景组织](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html)支持自包含场景与显式依赖；[工程组织](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html)提供就近资源和命名建议；[UID 说明](https://godotengine.org/article/uid-changes-coming-to-godot-4-4/)解释 sidecar 的版本控制要求。其余是适合本工作区的小团队综合准则，不声称官方强制规范或跨项目验证完成。
