# 交付与版本流程

核对里程碑范围、运行入口、验证证据、已知问题、恢复信息和下一步。技术测试通过只能证明其覆盖范围，不能替代用户对核心体验的认可或真人试玩。

提交应只覆盖当前交付范围；更新 CHANGELOG 记录可定位变更，NOW 记录新的当前工作。发布、外发和商店操作需要独立授权。

## 启动入口与玩家分发

开始生成试玩包时，项目根至多保留一个当前游戏快捷入口。开发诊断入口集中maintenance/previews；builds按目标平台分层，再区分独立packages、需引擎的候选packs和历史archive。采用其他命名时在项目配置中明确映射；各受管目录README逐层路由，健康检查应拒绝入口散落、当前别名失配及缺失路由。没有试玩包时不预建空功能或写死游戏名。

PCK加本机引擎启动器不等于独立分发。独立包须有匹配版本/可信来源模板、运行文件、玩家说明和公开许可，排除调试桥、内部制作与测试材料；默认dry-run、拒绝覆盖历史版本。ZIP解压后核对文件哈希，在移除开发工具环境且离开工程目录后实际启动，另验证包内相关行为。验证后才切换唯一当前入口，历史归档保全哈希并修复引用；已封版哈希绑定材料不直接改写，用迁移说明路由。跨机器、签名、商店发布分别保留独立验证与授权边界。

模板已提供builds/windows三类目录、maintenance/previews及通用check-build-layout.mjs；当前版本未设置时允许无启动器。首次交付后设置layout.json的current_release/current_executable，检查两个play.cmd的路由一致性；不会要求Git新克隆已有被忽略的大包。项目专属打包器在实际工程中维护，核对资源白名单、版本身份、原子输出及实际包启动，不从模板推定已有打包工具。

项目资源进入 [资源操作](assets.md)：同步用途清单、版本、引用与门；保留历史和原文件哈希。

交付状态变化后执行[状态维护](status.md)：先更新权威结论，再复核消费者，历史退出当前入口。真实里程碑/重复返工时复用现有复盘，区分项目问题、方法增量与接线遗漏，多源检验归因后交所属流程；无增量不新建空记录。不得从测试通过推导用户接受。
