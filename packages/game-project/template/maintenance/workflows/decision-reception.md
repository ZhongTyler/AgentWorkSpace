# 既有决定接收与持续消费

目的：避免把“本版未实现”当成“尚未决定”，或用原型的局部例外覆盖完整产品方向。接收索引不是第二套设计 SSOT，也不是新一轮批准。

## 初始化、接手或收到新来源

1. 盘点有效输入：原始需求、正式决定、已接受简报、原型实际规则及后续用户反馈。记录来源版本或规范化文本 SHA-256；只给入口链接不算接收完成。
2. 在 [决定接收表](../../docs/decisions/decision-reception.md) 逐项标明去向。覆盖来源决定全集，包括暂缓、被替代和不属于本次切片的决定；大来源可分组路由，但必须可核对遗漏。没有 Brainstorm 也照实际来源执行；没有旧来源则保持空表，不制造决定。
3. 区分决定处置与实现证据：`inherited` 沿用、`deferred` 已定但暂缓、`scoped-change` 特定版本采用不同规则、`superseded` 有明确替代、`needs-review` 存在冲突或缺来源。是否已实现、验证或验收由链接目标拥有，不能从这些处置词推断。
4. 改变或替代必须回链真实授权及适用范围；暂缓须写恢复条件。示例数值、建议和未采用候选不能升级为决定。原档案不改写，不复制全部聊天；仅在源不可随交付访问且已有授权时保存可追溯快照。

## 讨论、写 Spec 或实施前

先查当前问题相关的接收项及权威原文，再区分“已定方向／待定细则／真实冲突”。既有明确决定直接继承，不重复请用户决定。源版本改变、原文不可达或冲突未解时，不猜测；保留阻碍，只暂停依赖该缺口的讨论或实现，独立部分继续。

原型范围排除仅表示当版不做；正式开发应复核延期项，而不是默认为永久取消。后续正式决定只更新受影响的接收项及当前 SSOT，保留原来源与替代关系。当前工作入口必须能路由到本表。

## 检查与维护

健康检查读取表内 `decision-reception` JSON 登记的来源及 Markdown 行：核对来源文本哈希、声明的 ID 集合、重复／遗漏、处置、当前文档和替代证据链接。`id_pattern` 是带一个捕获组的逐行正则，用于定位来源的稳定决定 ID；来源无稳定 ID 时先按原段落建立可追溯标识，不伪造原有编号。

表的列固定为“来源:ID／处置／接收摘要／当前归属／变更依据／下一动作”。JSON 中路径相对项目根，表内链接相对表文件。源码换行统一 LF 后计算哈希；内容变化须先复核受影响项，再刷新哈希，不能为了通过检查自动盖章。空模板 `state=empty` 不是“接收通过”；有来源时用 `state=received`。已有等价索引可迁入这些列，不再维护两份。

检查不能判断摘要是否忠实、发现未登记来源或证明授权真实；接收者仍需语义核对。新来源不得因不匹配 ID 格式而默认为零决定。未来实际接手时观察是否减少重复提问和遗漏，不把结构 PASS 宣称通用效果已证明。
