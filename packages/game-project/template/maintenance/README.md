# 维护层

本目录是所有工作操作的第一入口。先识别操作类型、影响范围与当前项目状态，再进入对应流程；只读任务不自动写入或修复。

## 目录

- [previews/](previews/README.md)：开发预览与诊断入口，和玩家包分开。

- [workflows/](workflows/README.md)：新增、修改、删除、文档迁移、交付与升级流程。
- [scripts/](scripts/README.md)：只读健康检查和项目初始化工具。

## 关键文件

- [project-config.json](project-config.json)：项目身份、模板版本、引擎位置与健康检查边界的 SSOT。
- [CHANGELOG.md](CHANGELOG.md)：已提交或可定位的项目变更，不记录即时工作状态。

## 结构变更与模板同步

新增、删除、移动或调整目录结构、文档分区、入口路由、维护脚本及检查配置时，必须识别是否影响项目模板，而不等用户再次提醒。

- 变更属于可复用的项目组织、维护或交付约定时，在本次任务中自动同步所属模板的相关结构、README路由、配置、忽略规则、流程及检查；只同步实际受影响部分。
- 游戏专属内容、素材、版本身份、运行产物和临时试验不直接复制进模板；提炼通用部分，保留空模板可初始化、无游戏依赖的状态。不得据此批量改动其他既有项目。
- 同步前核对模板位置、现有内容及owner；同步后分别验证项目和模板（健康检查及受影响测试），按父子仓关系完成提交。模板不可达、冻结或存在重叠owner时，不强行覆盖；保全待同步项、原因和恢复入口，不宣称已同步。
- 收尾简要记录“已同步哪些内容”或“无需同步及原因”，复用本次变更/交付记录，不新增独立台账。健康检查只能验证结构，不能代替是否通用的判断。

## 既有决定消费

初始化、接手及新功能讨论/Spec前，按 [决定接收](workflows/decision-reception.md) 核对旧决定去向；先查相关原文与当前归属，区分已定方向、未定细则和版本差异。暂未实现不等于尚未决定。健康检查覆盖接收表完整性，不代替语义判断。

## 路由顺序

表现类任务可接入工作区 GamePresentation/README.md（若宿主有该模块）；由其提供方法和资源引擎交接，本项目仍拥有设计、进度和验收。初始化时解析宿主位置，不把模板所在路径复制为项目依赖；缺少该模块时不假设存在，不阻断普通开发。

1. 读取项目根 `README.md`、`NOW.md`、本目录配置和与本次操作相关的领域文档。
2. 选择 [workflows/](workflows/README.md) 中的流程。
3. 实施后运行 [scripts/](scripts/README.md) 中与影响面相符的检查，更新受影响的 SSOT、NOW 或 CHANGELOG。

资源增删改先进入 [资源操作](workflows/assets.md)，清单与来源在 [工作台](../assets/README.md)。

状态变化先按[状态维护](workflows/status.md)复核权威与消费者，摘要不追加多套“当前”。重要判断和反例按可达宿主的支持与学习约定识别缺口；没有该入口时沿本项目事实、决定与验证记录继续。资源和分析各自的权威归属不变。

## 脱离模板库后使用

本项目是独立副本，不需要模板库在运行时存在。GamePresentation、FromDemoToSpec、Knowledge、Research、GameAnalysisDecision、Skills 和 Tools 都是可选支持；按实际宿主导航定位已安装模块或经过审阅的替代流程，不把名称相似当作接口兼容。资源合同未配置时可保全和检查已有材料；真正发布资源前另行确认可达合同、授权和验证。
