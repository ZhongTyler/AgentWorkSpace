# 常驻游戏设计与游戏拆解研究

这是 Research 的专业研究路线：主动寻找有用设计方法、拆解可迁移的游戏机制，并将可靠材料交给 Knowledge 自动消化。研究方法、正式决定与知识库各有原 owner，不新增第二套 Wiki 或独立专家框架。

## 来源与分工

复用[通用正式池](../sources.json)，并增加[游戏来源目录](sources.json)的十组正式来源。正式表示可以按问题选用，不表示全站正文、视频和账号都已接通。

| 来源 | 用于什么 | 获取路径及当前边界 |
|---|---|---|
| [Game Developer / Design](https://www.gamedeveloper.com/design) | 机制、关卡、试玩方法、开发复盘 | 网页检索与选定正文；已读取具体试玩文章，报道须追演讲或原作者 |
| [GDC Vault 免费区](https://gdcvault.com/free/) | 设计演讲与具体游戏复盘 | 免费索引可读；视频、字幕与幻灯片逐项检查，简介不等于已看演讲 |
| [机核 DESIGN](https://www.gcores.com/design_and_art) / [BOOOM](https://site.gcores.com/booomlab/about/) | 中文开发者分享、独立游戏案例 | 网页；分类含美术和新闻，需筛设计增量，付费内容跳过 |
| [GameRes 游资网](https://www.gameres.com/list/24) | 中文设计/产品拆解、开发者复盘 | 分类与具体正文已可读；核对转载原作者/原链接，必要图表另读 |
| [indienova](https://indienova.com/blogs/all) | 独立开发日志、设计文章、GDC中文编译 | 一个GDC编译正文已用普通公开HTTP读通；检索工具可能403，编译不等于原讲完整转录 |
| [GMTK](https://gamemakerstoolkit.com/) | 设计机制、游戏案例与制作过程 | Balatro实例已导出并完整读取原生英文字幕、查看10处有效关键画面；其他视频逐项验收 |
| [Deconstructor of Fun](https://www.deconstructoroffun.com/blog) | 系统、循环、留存与商业化拆解 | 网页；偏移动/F2P，估算数据与设计因果分开 |
| [Factorio 官方日志](https://www.factorio.com/blog/) | 一手机制迭代、原型与生产取舍 | 网页；已读 FFF417，不把团队经验直接普遍化 |
| [DiGRA 学术库](https://dl.digra.org/index.php/dl) | 玩家研究、设计理论与研究方法 | 索引已可读；选论文后取全文/PDF，摘要不作完整消化 |
| [Steam](https://store.steampowered.com/) | 官方版本更新、玩家反馈与问题发现 | 已有只读 Steam MCP；本轮公开更新读取成功，样本评价不代表全体玩家 |

知乎优先专业作者/专栏及其原始出处；Reddit 看 gamedev、gamedesign 和具体游戏社区的失败场景；GitHub 核查机制实现与版本；HN、掘金用于发现相关案例，HF 仅在 AI 游戏问题需要时选用。通用来源的暂停/放弃规则在游戏线同样有效。

游戏站未核实专用 MCP 时使用现有网页能力；有经过验证的 RSS 才接现有 RSS MCP，不猜订阅端点、不为每站重复安装工具。Steam MCP 是宿主已有可选能力，未纳入 Research 的固定依赖归档；缺它可读公开官方网页。视频文字获取与当前实测见[视频到文字](video-text.md)，访问缺口保留，不因纳入正式来源而消失。

## 穿插在来源中的筛选维度

同一个游戏或演讲可能出现在知乎、GameRes、GDC和开发者博客；用[跨来源维度](selection-lenses.json)从问题出发交叉发现，不将平台热度直接当含金量。

| 维度 | 具体锚点 | 用法 |
|---|---|---|
| 奖项与提名 | TGA、BAFTA、D.I.C.E.、GDCA；独立方向优先IGF、indiePlay | 记录年份、类别、提名/获奖与评审类型。研究关卡/系统优先相关设计类别，不只追GOTY总奖 |
| 专业分享 | GDC设计轨道/复盘、CEDEC/CEDiL | 从设计问题找讲者、完整材料及项目实践；GDC正式征稿与Sponsored Sessions区分，未读演讲不背书内容 |
| 一手性 | 设计者说明、官方开发日志、被放弃的方案 | 优先还原“为什么这样选、替代方案为何不选”，仍检查自述偏差 |
| 可复核性 | 完整字幕/图表、可玩Demo、代码/补丁、定位明确的观察记录 | 提高深读优先级，核对实际版本和读到的范围 |
| 适配度 | 机制/类型、平台、团队规模、预算周期、开发阶段、目标玩家 | 先看能否解释当前问题和低成本迁移，大作方法不能直接套小团队 |
| 失败和长期反馈 | 未达预期复盘、不同版本、玩家误解、同机制不同结果 | 补成功样本与奖项筛选的偏差，避免只学赢家 |

这些维度提高候选发现优先级，不另设总分或硬性获奖门槛。选择顺序是当前问题与适配度 → 材料/一手证据 → 相关专业认可；低成本高潜力的新方向即使未获奖仍可试。通常每轮只用一两个维度围绕一个主题有界发现，不把维度数乘成检索预算；正式消化优先3–4篇、最多6篇相关来源。

例如研究“卡牌信息应该显示多少”：先找相近机制及相关IGF/BAFTA设计案例，再跨GMTK、GDC、GameRes、indienova寻找解释，追设计者原话/实际版本，并找相反玩家体验；奖励信号帮助选案例，结论仍由证据和可迁移条件支持。具体版本未核实的旧转录不得当作当前游戏规则。

## 两条研究问题

**设计方法**：围绕当前项目的真实缺口，查机制、条件、失败案例及验证办法。例如核心循环、决策空间、信息可读性、难度节奏、经济/成长、关卡、试玩反馈与原型范围。先查已有 Knowledge，避免把已有常识再写一遍。

**具体游戏拆解**：先说明研究哪一段体验、哪个版本和为什么值得比较。记录玩家目标 → 行动/反馈 → 资源与约束 → 有意义的选择 → 节奏/进度 → 体验意图；再解释系统如何相互作用、哪些替代解释或失败场景会推翻结论、什么条件可以迁移到当前问题。不要求每次全游戏百科拆解。

证据标签按实际保留：开发者自述、完整论文、真实游玩、演示/视频观察、玩家评价。没有实际玩就不得写成已玩；销量、留存、好评与某机制存在相关性也不能单独证明因果。Game Developer 对 GDC 演讲的报道与原演讲可能同源，不算两份独立验证。

## 日常入口与每周运行

- 用户给 MD/网址：先读材料 → 查既有知识 → 按缺口补查少量来源 → 同一研究报告 → 有用材料自动消化。用户限定只分析所给材料时不扩大检索。
- 用户给设计问题/游戏名称：先限定用途和观察范围，再按上述两条路线取证。
- 每周一、周四18:00北京时间主动探索：沿[每周合同](../proactive/README.md)，约80%当前项目/已有主题、20%相邻方向。围绕一个主题，正式进入Knowledge消化前优先找3–4篇相关且有增量的来源，最多6篇；不足不凑数，可以少于3篇。其他有用主题去重排队。发现约30分钟，后续完整消化不以该预算降质。每轮独立判断游戏资料的发展速度、重复率和积压，必要时申请调整游戏路线频率，用户批准后再改变调度。

日常正式游戏研究也采用上述主题批次：围绕同一缺口补互补案例、原作者解释和反例，避免只读一篇就抽象通则；同文转载、译文和原帖计同一证据链，每篇仍独立保存身份与Raw，不合并来源证词。短问答、只分析指定材料或不进入消化的任务不强制补篇。图片/图表/GIF与视频关键画面见[媒体采集](media-capture.md)，网页工具见[浏览器工具](../integrations/browser/README.md)。

Research 只保存队列与研究判断，长期原文和 Raw/Wiki 由 Knowledge 拥有；需要项目决策时按宿主要求交 Knowledge Query / GAD，不自动改 GAD 原则或项目 DEC。原有暂停的 GAD 周月学习维护保持暂停。

## Knowledge 自动消化接线

使用者明确授权后，有用游戏材料可按宿主合同自动消化；安装本包不授予该授权。宿主未安装 Knowledge 时只保存研究和可恢复交接，不声称已经入库。安装后的当前 Knowledge 合同优先于这里的路线说明。

1. 先按 canonical URL、原始出处、版本/内容身份查 `raw-sources` 与 scoring 记录，复用已消化项；新增确有价值且证据完整者才入选。排队不是已入库。
2. 抓取完整正文、作者/日期/来源和必要媒体清单；图片、图表、视频内的关键含义需要实际读取。只有搜索摘要、演讲简介、未看必要视频片段或缺关键媒体时保留捕获缺口，不交 writer 编造。已有同文缺媒体走补证/修复，不伪造新篇增量。
3. 读取 Knowledge 的 `AGENTS.md`、`README.md`、`RUNTIME_ROUTING.md`、`INGEST_PROTOCOL.md`、`INGEST_WRITER_ROUTING.md` 及其执行入口。核对活跃 registry、Git/owner；沿同一未完成批次恢复，冲突先排队，不把所有有用材料无限塞入本轮。
4. 自动消化使用当前 `deferred + core`；新普通批次依合同走 `consolidated-v1` / `advance`。主复核配置需实际为 `gpt-6-sol / medium`，writer 为单一 `gpt-6-luna / xhigh`，不继承历史；核对宿主身份/配置和日志，不用自报代替验证。若探索会话配置不同，交给显式固定配置的 Knowledge 协调会话；该会话是否可被原生控制器绑定必须实际验证，不能预称支持。配置/控制器不支持时保全捕获与准确阻塞，后续在合规会话恢复。
5. writer 写 Raw/Wiki，主复核不写正文；完整 source↔Raw、Raw→Wiki 核查。先 Raw checkpoint，后 Wiki；优先现有 Wiki，新页、评分、媒体、作用范围均按 Knowledge 合同，不自动扩建 Domain/Group/shared 原则。
6. 自动推进至已验证 `awaiting_final_review`，向用户一次交汇总报告与当前精确哈希；仅用户批准该版本后才能 Finish 和逐级父仓 gitlink 闭合。本次常驻自动化授权不能充当未来报告的批准。同一哈希已通知且内容未变时，不每周重复提醒；保留停点，等待批准期间不重叠启动新批次。若控制器要求 checkpoint，按当前合同保存，不提前宣称整体入库完成。

候选记录只需来源、用途、完整性/媒体、去重、当前阶段、Knowledge 批次/产物链接和下一动作。自动审核/预算/失败以现有控制器为准，不另造一套 PASS 或绕过终审。暂时抓取失败先尝试其他正式来源，只有影响关键研究或持续阻塞消化才通知用户。

## 使用后的闭环

每项可迁移结论注明适用条件与建议验证：用于哪个问题、预期改变什么、怎样用有界原型/真实试玩区分。真正应用后把结果回填原研究，并按 Knowledge/GAD 的现有维护授权更新；资料积累、技术通过、真人体验与设计决策效果分别记录。每四次周运行评估重复率、可用增量、实际采用与反馈、人工介入和成本。

## 每轮简报

有用独立增量、新保留的条件候选和改变判断的反例按[主动研究简报](../proactive/reporting.md)向用户报告一次，即使暂不采用；说明可迁移机制、处置理由、下一动作、Knowledge实际阶段及是否需决定。同一候选或同一终审哈希无实质变化不重复通知，纯重复和无价值增量保持静默。

可选模型遵循[选择、效果记录与复盘模板](../templates/decision-model-policy.md)。使用者明确授权后，Agent可自行判断是否调用及选择已配置backend，记录model_decision与实际tool_usage、纠正/回退和端到端成本，沿宿主既有窗口复盘调整。安装不启用该授权；未配置、失败或无增量时保留原研究路径，不自动下载模型、登录或新增任务。
