# 性能定位与对象复用

帧耗时、分配/回收峰值或池化后串状态时使用。先确定目标设备、场景规模与帧预算；保留同场景的基线、尾部帧耗时、内存和质量条件。60FPS、LOD、ECS、零分配不是每个游戏的统一门；平均FPS不能解释短时卡顿。

## 从瓶颈选手段

- CPU逻辑/物理：实测热点与调用量，再考虑缓存、碰撞过滤、空间分区或分批更新；分批会改变响应延迟与顺序，不能只看单帧用时下降。
- GPU/提交：核绘制、材质、透明叠加、纹理与带宽；批处理、实例化、LOD/遮挡按当前引擎和画面取舍使用，不按旧教程阈值断言瓶颈。
- 分配/加载：区分对象生命周期、托管GC、原生/显存和I/O。值类型临时值不自动等于堆分配；复用StringBuilder也不保证整条UI更新零分配。异步加载不消除主线程激活/上传成本。
- 数据密集更新：组件数据与系统分离、连续布局可有价值，但ECS骨架不等于可用存储。按实体身份匹配组件，不能因为两个数组长度相同就假定一一对应。没有实际规模与热点，不重建架构。

## 池化需要所有权，而不只是容器

针对频繁创建且成本显著的对象，优先宿主已有池。区分“最多保留多少空闲对象”和“最多允许多少活对象”；耗尽时扩容、拒绝还是降级要明确，预热本身也有成本。

租出/回收保持唯一所有权：拒绝重复回收与其他池的对象；有迟到回调时用租约/世代避免旧回调归还已重新租出的对象。回收按对象职责清理速度、伤害、目标、计时器、订阅、协程、碰撞与表现；只隐藏或停Tick不代表状态干净。清理失败时不把半复位对象重新入池。

验证本次实际副作用：同一实例不会同时租给两人，归还后无旧事件/定时器，下一租次得到初始合同状态；正常创建路径与池耗尽/销毁也覆盖。是否节省看相同工作负载的完整成本和保留内存，不只比较new次数。

## 相邻模式的边界

状态机检查Exit/Enter次序、重复进入、重入和异常政策；别因加了状态类就假定订阅已清理。事件系统Subscribe/Unsubscribe成对不防重复Subscribe，重复启用与失活后的回调需要核验。双缓冲要求当前/下一缓冲真分离，交换引用不负责清空下一帧数据。Command Undo必须说明作用域，撤销一个位置不自动撤销声音、网络或存档副作用。
