# 01 需求与研究范围

> 便携版以trip.json及knowledge为正式输入，sync/build派生总表与网页。本章负责模型/人的语义判断；确定性步骤见[角色与步骤](../运行/角色与步骤.md)。

输入：用户描述、已有攻略、收藏/链接、订单、日期范围。输出：旅行边界、研究覆盖矩阵和有优先级的缺口。

## 先建立约束

使用[需求模板](../模板/项目/需求与偏好.md)。先从已提供资料提取，未知项按影响区分，不重复询问用户已经决定的事项。

用户指定偏好档案时，按[偏好机制](../模板/偏好记录.md)记录本次采用与覆盖，不自动读取其他人的档案。亲历反馈的处理见[复盘](../运行/旅后复盘与阅读优先级.md)。区分“去过且喜欢”“只是计划过”和“别人推荐”。

| 约束 | 要具体到什么程度 |
|---|---|
| 日期与时区 | 实际当地抵达/离开日期、跨午夜和夏令时、可游览的半天 |
| 同行 | 每段人数、分组/会合、儿童或行动需求、驾驶员；不假定全程人数一样 |
| 固定锚点 | 交通、住宿、已订活动/餐厅，集合而非仅开场时间，入住/退房 |
| 偏好 | 体验优先级、咖啡/饮食、自然/城市/博物馆、驾驶和步行耐受 |
| 成本 | 每人/全队、包含哪些项目、币种与换算口径；未定预算先报区间 |
| 节奏 | 早起接受度、午休、采购、摄影、日落与夜间活动后的恢复 |
| 行李与车 | 是否寄存、车何时取还、实际车型/空间仍以订单或交付为准 |
| 交付 | 研究稿、逐日执行、手机网页、离线包、分享对象与私密资料范围 |

不要把这次「每天一家咖啡、晚餐可自炊」预置成所有用户都要的活动；可把它们作为偏好问项。明确不考虑的项目记在决策记录，后续研究不自动复活。

## 如果交通与住宿还没有订

先按日期与地区比较骨架，再研究细部：进出城市、住几晚、自驾还是公共交通、是否需要移动住宿。未购买的价格和余位都是查询快照，不承诺以后可订。

- 航班/铁路：机场与航站楼、门到门、转机与行李是否直挂、总票价含行李、抵达后的末班交通、退改条件。
- 住宿：准确区域与到核心活动的时间、入住退房、人数与床型、厨房/停车/寄存、清洁税费后的总价、取消规则；不要用城市中心点代替真实住处算日程。
- 租车：取还点与营业、异地费用、人数/箱包、驾驶资格与支付要求、保险/自付额、道路与轮渡收费、加油充电。清单用于核对条款，不代替适用法律或保险合同。
- 入境/健康：按旅客实际国籍、证件和路线查询官方签证/转机/入境要求；保险覆盖需按实际徒步、驾驶或海上活动核对。敏感证件不进入共享网站。

使用[预订前比较与预算](../模板/预订前比较与预算.md)按同一口径比较。推荐不等于下单，实际预订/付款另按授权执行；订单到达后进入订单事实源，不保留另一份手工「已订」表。

## 新城市先保证覆盖

按时长、资料可得性和用户投入要求设定规模目标，不预设统一篇数。数量不是通关线，同质咖啡笔记不能代表机场、交通和景点都已研究。

至少审视：抵离交通、市内交通/票务、住宿区动线、景点与活动、晴雨/季节/体力差异、餐厅、咖啡、超市/自炊、购物、支付通信/安全、周边一日游。兴趣强项加深，低相关项明确不适用。

[研究覆盖模板](../模板/研究覆盖与消化记录.md)逐格写：问题、已有Wiki、有效经验ID、官方来源、尚缺证据、是否阻塞。来源相互抄袭或同一作者重复内容不视作独立交叉印证。

## 收敛与停止

可以给一版方案的条件：

1. 关键转场与固定锚点能衔接，有证据支持的可行默认线。
2. 重要体验有选择依据；营业、票务、路况等关键限制能核实或有可用备选。
3. 餐饮、采购、行李、日照与恢复时间没有明显断点。
4. 未决项能区分为阻塞、需用户选择、临近复查、可选升级。
5. 未完成研究如实列出，不能靠凑数写成「覆盖完整」。

新增资料不再改变选择、时间、成本、风险或备选时，可以停止该主题。找不到足够经验材料时记录尝试与缺口，官方补证另计；不要反复无限搜索。

## 一日游与替换机会

比较「城内多一天」与「周边一日游」：往返门到门、班次锁定、独特体验、天气依赖、费用和失去的城内内容。真正可替换才作为方案，不把周边清单全部塞进每日计划。

本环节的非阻塞未知项可带入下一环节；真正会改变整段可行性的日期、住宿位置或固定票务缺口才集中向用户确认。
