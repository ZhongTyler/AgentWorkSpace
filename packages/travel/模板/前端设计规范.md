# 前端设计规范 · 模板

保存为项目 `frontend/DESIGN-SPEC.md`。这是规则和设计理由，不是旅行状态或验收报告。与 `contract.json`、少量 `fixtures.json` 一起交付；页面是消费这三者的实现。

## 1. 基线与职责

- 基线 ID：与 `contract.json.baseline` 相同。
- 范围：覆盖的页面、阅读任务、不适用场景。
- 设计负责人：角色或交接记录；不绑定某个模型。
- 用户认可依据：实际讨论或审阅记录的引用；未认可写“待认可”。脚本通过不等于认可。
- 变更规则：见[前端分工](../运行/前端设计与内容分工.md)。建立经过认可的设计基线；内容更新不擅自改版，设计变更有负责人和回归检查。

不要在这里写“当前 N 天 / 没有预订 / 所有路线待定”。这些来自事实源；验收截图、检查结果和当次缺口写项目报告。

## 2. 阅读层级与视觉语言

一句话写清核心阅读任务。按“现在做什么 → 关键时限与导航 → 条件和备选 → 背景与来源”排列；主操作、地点入口、来源链接应有可辨别的载体。

- 令牌唯一值源：填写实际 CSS/主题文件路径。合同只引用令牌名；本文说明用途，不复制色值和数值表。
- 说明标题、正文、时间、辅助信息、警示分别用哪些令牌，以及位置、边界、字重如何共同传义。
- 断点和布局值由代码拥有；这里解释手机导航、折叠、允许横滑的容器及长内容处理。
- 可访问性目标：正文对比至少 4.5:1，独立触控入口至少 44px；焦点可见、键盘可操作、尊重减少动态效果。实测与否留在报告。

## 3. 页面与组件

逐个说明覆盖的页面、区块顺序和主要操作。路由、选择器、屏宽及检查条件写 `contract.json.views/widths`，不在两处重复维护检查表。

每个组件说明：

| 项 | 填写内容 |
|---|---|
| 阅读用途 | 用户在这里完成哪个判断或动作 |
| 输入绑定 | 引用合同里的 binding ID；完整字段映射只在合同维护 |
| 正常 / 空 / 缺失 | 什么条件触发、显示或隐藏什么；不能写死当前旅行状态 |
| 待定 / 已订 | 从真实订单或路线字段派生；新增数据后旧空态必须消失 |
| 长内容 | 换行、展开、独立详情或编辑压缩；不要截掉集合时刻、安全条件 |
| 交互 | 打开、关闭、返回焦点、切日期保留什么、刷新恢复什么 |
| 禁止推断 | 不自行计算路网 ETA、不将参考营业时间显示为实时营业中等 |

Wiki 用稳定 ID 关联，不把某一趟旅行的文件名硬编码到组件。

## 4. 字段与状态合同

从[机器合同模板](前端组件合同.json)复制后，按项目真实字段和组件改写。格式、命令和已知检查边界见[前端分工](../运行/前端设计与内容分工.md)。

必须覆盖所有用户可见数据槽位，包括 `trip.json 字段 → generated/data.json 字段 → 组件`，并给短文案写长度/换行规则。天气等衍生数据标 `derived`，在本文说明实际来源与推导方法；不要把衍生字段反写成新事实源。

`fixtures.json` 至少覆盖有数据、空、缺字段和长内容。预订、路线、天气、筛选等有状态的组件应有成对断言：正确内容出现，过时空态消失。合成测试数据不进入事实源，也不出现在正式网站。

### 4.1 状态文案的进出条件（必填）

空态和提示不能只写"长什么样"，必须写"什么时候出现、什么时候消失"。规范里给一张表，至少覆盖下列状态，每行都要落到 `trip.json → generated/data.json` 的具体字段与判断式：

| 状态 | 出现条件 | 退出条件 | 依据字段 |
|---|---|---|---|
| 尚未预订 | 没有 `status:"booked"` 的订单 | 出现第一条已订订单 | `orders[].status` |
| 部分已订 | 有已订订单且仍有 `kind:"booking"` 的 open 待办 | 预订类待办全部关闭 | `orders[]`、`todos[].kind/status` |
| 路线待定 / 部分待定 / 已定案 | 按 `pending` 段数与总段数比较 | 待定段清零 | `routes[].pending` |
| 坐标缺失 / 已登记 | 有地点缺 `places[].location` | 全部地点补齐坐标 | `places[].location` |
| 天气未留档 | 没有任何带 `daily` 的天气快照 | 补入任一天气快照 | `weather[].daily` |
| 自定义提示（价格口径、临时公告等） | `presentation.notices[]` 有条目 | 条目删除 | `presentation.notices[]` |

三条硬规则：

1. **页面里不得出现状态字面量**。所有"尚未预订 / 全部待定 / 未留档"一类文案由数据推导；数据变了文案必须跟着变。
2. **提示与条件是同一份事实**。写死一句"车票住宿门票均未订"，等于把当天的数据快照抄进模板。
3. **验收要有变体，不只对当前样本**。至少跑三档：全空、部分、全满；每档断言"该出现的出现、该消失的消失"，并用内存数据副本构造，不写回事实源。

## 5. 交付和维护

- 自包含模板适配器：`frontend-build → frontend-check → frontend-audit`，命令均带 `--project`；先通过结构与字段检查，再看浏览器截图。
- 其他前端技术栈：保留同样的字段/状态合同，使用自身构建和测试适配；未接线明确报告，不能套用通过结论。
- 报告绑定输入及页面指纹，分开写脚本结果、编辑者看图、用户认可。样章认可后仍要覆盖全部真实页面和日期；合成测试台不代替全旅程巡检。
- 设计变更记录只写基线版本、原因、影响和审阅入口；当前旅行待办仍归事实源。

不必另建庞大规范目录。三份文件足够；测试报告和构建回执是可再生成的证据。
