# 前端设计与内容分工

建立经过认可的设计基线；内容更新不擅自改版，设计变更有负责人和回归检查。设计负责人是角色，不是某个模型；可由同一执行者承担多种角色，但不能代替用户认可。

## 三份轻量交付

| 文件 | 唯一职责 | 不放什么 |
|---|---|---|
| `frontend/DESIGN-SPEC.md` | 阅读层级、组件语义、交互边界、设计理由、认可依据 | 当前天数、订单数量、测试通过声明 |
| `frontend/contract.json` | 源字段→投影→组件绑定、槽位限制、令牌引用、路由和屏宽断言 | 复制一套令牌值、旅行事实、人工认可布尔值 |
| `frontend/fixtures.json` | 少量合成状态与可验证预期 | 用户订单、私址、真实登录资料 |

起点：[规范模板](../模板/前端设计规范.md)、[机器合同模板](../模板/前端组件合同.json)、[合成状态](../examples/frontend/fixtures.json)。CSS/主题文件拥有令牌值；`trip.json` 拥有结构事实；`generated/data.json` 只是投影，不能编辑。Wiki 用 ID 关联。

## 谁可以改什么

| 类型 | 执行者与验证 |
|---|---|
| 内容更新 | 内容维护者可改既有类型条目、价格、营业、文案、顺序；重新生成与核对。安全或取消条件不能为压缩字数而删掉 |
| 缺陷修复 | 执行者可修复违反已认可基线的错位、断链、空态不消失、溢出；补对应反例并回归。不必重新设计，也不要求换模型 |
| 基线内调整 | 已授权范围内的换行、间距、焦点等调整，由设计负责人复核受影响组件和屏宽；同步合同/规范中实际改变的规则 |
| 重新设计 | 新页面、主信息层级、新交互或视觉方向变化，先说明影响、获得相应认可，再更新基线并全量巡检 |

超长先判断能否按既有规则换行、展开或精简冗余；必须改变信息层级或删关键条件才算新设计问题。不因未知边界回滚用户数据；只隔离尚未认可的展示改动，继续不依赖它的工作。

## 机器合同格式 v1

项目将 `template/output/spec/fixtures/tokenFile` 声明为 `frontend/` 内的相对路径。适配器只接受内联 CSS/JS 的 HTML 模板，且恰有一个 `__TRAVEL_DATA__` 标记，位于 `application/json` 数据脚本中。令牌值仍由 tokenFile 拥有，`tokens` 只列必需名称。可先在干净演示项目把 examples/frontend 的模板和状态文件复制到 frontend，再填写规范与合同；这只是功能测试台，不是成品设计。

`bindings` 每项包含 `id/component/source/projection/transform`：

- 路径采用 `days[].summary` 这样的对象字段/数组通配；不执行表达式。
- `identity` 检查源与投影对应值相等；`pending` 检查源是否等于字符串 pending，并对应投影布尔值，例如 `routes[].status → routes[].pending`。
- `derived` 用于天气快照、加工后的 Wiki 等衍生输入；省略 source，推导由投影器和专门测试负责。此声明本身不证明推导正确。
- `required` 要求已有条目不缺值；空集合仍可合法，是否必须有条目用页面 count 断言。
- `maxChars` 按 Unicode 码点计数；`multiline:false` 禁止换行。短槽位设上限，长文用详情，不把上限变成删除事实的理由。

`views` 是实际路由及 DOM 断言。选择器支持 `count/includes/excludes/visible`；当前数据的数量预期由实现方按数据生成断言或更新测试，不能在规范中固定某趟旅行的总数。`widths` 至少含 320、390 和一个不小于 1280 的桌面宽度。

`fixtures` 文件是数组，每项 `id/state/patch/views`；state 至少覆盖 populated、empty、missing、long-text。patch 只在测试页浅替换投影顶层集合，不改 trip.json；相关组件必须写具体断言，不能仅换 state 标签。这里测试渲染状态，源到投影由绑定检查和核心测试另验。合成数据不自动获得完整业务有效性。

## 执行顺序

```sh
node scripts/travel.mjs frontend-build --project <项目>
node scripts/travel.mjs frontend-check --project <项目>
node scripts/travel.mjs frontend-audit --project <项目>
```

脚本分工：

- build：sync 后核对投影、绑定、长度和令牌声明；安全内嵌 JSON，写页面与 receipt。不执行项目自带脚本，不联网。
- check：只读检查完整投影是否仍等于当前源、绑定是否匹配、字段限制、声明的令牌是否存在、页面是否匹配模板/规范/合同/状态样例及源指纹。不解析全部 CSS，不自动发现漏登记的槽位或硬编码。
- audit：可选 Playwright；默认用已有运行时，环境参数与 browser-audit 相同。断网打开当前页面和合成状态，逐路由/屏宽检查断言、页面溢出、控制台错误和外部请求；生成 `.runtime/frontend-audit` 截图及 `reports/frontend-audit.json`。不自动安装浏览器。
- 编辑者：看图并覆盖漏登记页面、交互、对比度、长内容与语义正确性；对遗漏补合同。报告不自动宣称人已看图或用户已认可。

第三方框架不强制迁移模板。可接等价的构建/测试适配器，但必须报告哪些合同还未执行。既有项目不自动改造；下次设计维护时采用，不批量重建所有旅行。通用生成器的 build 回执和自定义 frontend 回执各自绑定实际产物，前者通过不证明后者新鲜。

## 完成标准

内容变化后必须验证状态随数据变化，不只是“页面没报错”。至少保留一个曾失败的反例，例如加入预订后“暂无预订”应消失。规范、模板或样例变动让旧回执失效，重新构建再验。全量页面与弹窗巡检继续按[视觉巡检](视觉层级与全量巡检.md)执行；自定义选择器需适配，不借用通用渲染器的通过报告。

交付只报告实际结果：结构、状态回归、编辑者审阅、用户认可、发布分别说明。未发布就是未发布。

工作流自身回归：`node --test tests/frontend-contract.test.mjs` 默认不需要浏览器；设置 `TRAVEL_FRONTEND_BROWSER=1` 后增加真实浏览器正例与故障注入测试，故意将订单栏写死为空态，必须在三个屏宽都被拦住。沿用上述可选浏览器环境参数；不自动安装或联网。
