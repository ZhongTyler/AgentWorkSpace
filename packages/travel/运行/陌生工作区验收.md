# 陌生工作区验收

检验新使用者能否依靠分发包完成有质量的旅行规划，不只是验证目录齐全和 build 可运行。一次通过只支持所测环境、任务和参与者，不证明任意目的地或任意人都能复现。

## 准备

1. 选择包内没有完成样章的新目的地。冻结简短需求：日期、人数、兴趣、节奏、预算边界及不可做的事。至少包含一个复杂日和一个转场/安静日；不用真实订单或私人住址凑状态。
2. `acceptance-prepare --workspace <新目录> --file <brief.json>`：只复制白名单工作流和需求，不带原作者目录、账号、旧旅行或服务器。字段示例见[试用需求](../examples/acceptance-brief.json)。已有目录拒绝覆盖。
3. 参与者只读该目录和获准的公开来源，从 README 开始。独立 Agent 须有相应授权，且不继承原任务对话；真人参与由使用者安排。文件分离不是操作系统隔离，必须如实记录。

## 从零完成什么

|阶段|实际交付|谁负责|
|---|---|---|
|上手|不查作者工作区即可找到入口、初始化、确认事实归属|参与者；脚本生成骨架|
|研究|按缺口收集官方和独立经验；正文/图片按实际保存和阅读声明，不要求登录账号|参与者阅读判断；导入/指纹/台账由脚本|
|综合|按主题形成 Wiki，关键结论有具体依据、范围、核验与复查日；冲突保留|参与者；claims-audit 验接线|
|规划|路线、门到门缓冲、核心体验、餐食咖啡、采购、订单与不确定性有默认和替换条件|参与者；validate/semantic-audit 查可确定错误|
|呈现|按设计技能与中文审校做短而具体的手册与执行面，真正构建离线网站|参与者设计/编辑；构建和浏览器检查由脚本|
|阅读验收|陌生读者用网页回答下面的问题，指出阻碍和理解成本|真人或独立 Agent，明确身份；脚本不作答|

未找到或无法取得的证据标缺口。地点没核准就给检索入口，不把有序点列当实测路线；远期天气不编造。不能将没有预订写成已订，也不能把菜单参考价写成目标日保证价。

## 读者要实际回答的问题

打开构建后的文件并操作，不只读源 JSON：

- 今天先去哪、为什么值得去，具体能体验什么？
- 几点必须到、哪里不能压缩，延误或坏天气时怎么换？
- 午餐和咖啡去哪里、为什么选、预算多少，备选何时启用？
- 导航指向哪里，是确切入口还是检索？返回和补给怎么衔接？
- 能否从一个关键结论找到原始依据和它的适用边界？
- 哪些是真正未决项、哪些已经可执行？有没有重复提醒、实现术语或长文字遮住重点？

逐项给具体页面/截图和答案，不能只打一个总分。保留严重错误、缺口与修改前后证据；必要时修工作流再从干净副本重试，不把修过的已见样本冒充第一次上手。

## 检查与报告

在新目录运行 `node workflow/scripts/travel.mjs acceptance-check --workspace .`。它检查需求未变、包未被改、结构、引用、来源接线和产物新鲜度，报告 `reports/engineering.json`。浏览器巡检、实际看图和读者回答仍另做；engineerPassed 不表示内容或体验验收。

报告只需一份，写环境、参与者/隔离方式、包/输入/产物指纹、真实完成链、尝试与失败、读者逐项答案、遗留问题和结论。分别列工程、编辑者阅读、独立 Agent 试用和真人验收；缺一项就写未做。不要计算虚假的人工时长或宣布普遍提效。来源包正式发布、网站部署和 Git 提交仍需各自授权。
