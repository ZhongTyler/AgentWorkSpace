# 体验指南与每日项目共用能力

适用：行程已采用，用户需要理解具体去哪里、看什么、怎么玩、怎么点餐，而不只是查看时间表。这是旅行手册与网站呈现环节的一项能力，不另加必用skill。

## 呈现与覆盖

手册保留城市／地区开篇，再给当天体验目录与具体模块；每日执行“项目”消费同一份当天内容和同一个组件。项目默认打开，时间就近提示，地图随手可开，餐饮/住宿收在当天工具，不继续平级占主入口。先试写一两天，认可后全程扩展。文风约20%杂志感、80%实用指导，按[阅读优先级](旅后复盘与阅读优先级.md)与[文案审校](旅行文案审校.md)执行。

从正式时间线、路线节点、默认餐次、活动订单及条件分支提取覆盖清单：

- 景点、街区、活动、餐厅、咖啡，以及正式体验的桥、湖、公路、轮渡均列出；即使只是车览也不能遗漏。
- 一项独立体验一条；停车、走到入口、拍照、返回通常合成一条。高原驾驶与独立观景台可以分列，但明确时长包含关系。
- 普通存包、取车、加油、入住、采购不凑数量，仍在原物流页签；纯转场日可零游览项目。
- 常规、条件、分组、替换分开计数；分组不代表每人全去，替换餐厅不代表吃两顿。数量从列表派生，不维护另一个手填总数。
- 默认外食和固定活动必须覆盖；候选库不整体搬入，已排除项目不复活。

## 内容与事实分工

每天拥有日期、概要、复核依据、体验列表与收尾提示。每项有稳定ID、placeId、标题、角色、方式、时长、必要条件、短正文和现场要点，可引用已有图片和Wiki。

正文回答：具体特点是什么；到达后先做什么再做什么；看哪里或点什么方向；何时收住。餐厅没有可靠招牌就写当天菜单的选择方法，不虚构必点。写清航行／候船、停车后步行／全程、包含在大窗口内／另外加时。

还需说明兴趣匹配和理解门槛：例如主要看画作还是实物，靠阅读还是直观场景，步行负担与可休息处是否已知。不要仅以“值得、震撼、推荐”代替内容。目录本身应可看懂一天，展开后再给现场步骤；不是每张卡都需要相同数量的小标题和提示。

价格、营业、预订、定位、分段路线仍由原事实源拥有，项目视图只引用。普通票未购不能标已订，酒店入口不能冒充独立餐厅。原URL、核验日期与未知边界保留，编辑文案不自动成为营业／路况实查。

图片复用已登记且适用于本用途的实景，保留来源、许可、年代／季节。无合适图可纯文字，不跨店、跨冰川借图。历史照片不保证当日景观。

## 更新与验收

1. 先更新拥有事实的总表／结构化行程、清单、地点卡或Wiki，再审阅对应体验。
2. 新增、移动或退出模块时检查旧日期残留、默认餐厅、分组、沿途节点、路线和订单关联。
3. 实际重读受影响内容后才更新复核摘要，不能脚本自动认可新事实。
4. 生成前检查全日覆盖、重复ID、失效地点／图片／来源、缺条件、过长段落和默认餐厅遗漏。
5. 浏览器比较两处同日正文一致性，覆盖计数、目录跳转、图片加载、地点弹窗、关闭返回、键盘、手机溢出；沿途节点和互斥分组需回归用例。
6. 重建离线包；发布仍按宿主授权及真实线上收据，不将本地成功写成上线。

## 宿主接线与边界

先检查实际schema。Markdown权威项目可增加体验JSON／文档并共用组件，不因此反向把总表变成生成物。便携版以trip.json为权威，启用时须一起扩展schema、生成器、渲染与正反例，不能只新增文档就声称支持。

便携渲染器已提供项目/地图双主入口及折叠工具，具体体验以trip.json.journal中kind=experience的段落供项目和手册共用；未标记的旧段落仍只作手册介绍。项目数量从实际条目派生，首项默认展开、目录可定位其他卡；时间与订单按同日placeIds引用。地图支持临时选点和会话保存，但增强角色与条件计数尚未成为通用schema。本章其余增强合同须按宿主实际接线验证，已实施项目的路径、颜色和技术栈不是通用要求。
