# 原型制作流程 · v2

FromDemoToSpec 的交付对象是足以验证完整核心体验的可玩原型，以及 Agent 可以继续消费的设计、工程和证据。V1 是第一次正式交给用户集中试玩的版本；80／90+ 是有条件的质量档位，不是 Agent 凭感觉打出的精确分数。

## 责任与自主边界

用户拥有目标、重要产品取舍、已承诺范围与核心玩法认可。Agent 负责整理输入、选路、实现、表现、内部检查、修复、追溯和准备交付。先减少用户实际阅读、判断、操作及中断时间，其次控制执行消耗；不能把基础 QA 转给用户来节省执行成本。

现有授权和决定跨轮持续。普通可逆实现按依据自主确定，将假设与用户决定分开。只有下一必要动作缺关键依据，或者会改变目标、已承诺范围、必要质量、预算或长期技术选择，才提出集中、具体、附推荐及代价的决策请求；同时完成独立的已授权工作。用户无需填模板或逐步批准表现校准。

在阶段真正切换、当前讨论目的改变或准备把判断交给用户时，用一小段状态说明公开：当前阶段、这一步服务的判断、已确认与仍未知、下一动作以及用户现在是否需要决定。它用于维持方向掌控，不要求每轮重复流程摘要，也不把普通实现重新变成逐步审批。

## 从输入到制作定义

输入可来自口述、概念简报、现成游戏或参考材料。保存原始来源，不覆盖其语义；Agent 整理[设计底稿](../templates/design-baseline.md)，能回答：

- 玩家要经历什么，关键选择、代价、即时后果与必要后续影响是什么？
- 一个完整闭环需要哪些系统、多少轮或成长阶段？哪些内容变体本版不做？
- 哪些操作、信息、音画与节奏是判断体验不可缺少的？
- 代码是否要沿用，运行／正式环境是什么，如何真正运行和检查？
- 已定约束、普通假设、关键未知、主要风险和执行投入边界是什么？

按实际信息推进，不固定问题数、可调参数数量、模板类型或单一可证伪假设。多个系统共同形成体验时保留其必要依赖，控制角色、关卡、素材变体等内容广度。明确玩法也可直接实现，不强制先 Brainstorm。

## 选择生命周期路径

有既有决定时，在制作定义阶段按[逐项接收](handoff-and-production.md#有效决定的逐项接收两条路径共同要求)登记其当前去向，包括本版不实现的已定方向。先读相关决定再提出问题；只留来源链接或仅摘录Brief不足以证明已接收完整约束。不改变原始决定，不把示例数值当规格。

Agent 根据代码后续用途与正式目标推荐路径；已有约束足够时直接确定并记理由。

| 路径 | 实现前必须明确 | 交付后的代码用途 |
|---|---|---|
| [single-file](../paths/single-file.md) | 原型运行环境、输入、离线／依赖约束及未来重建预期 | 小体量验证；正式阶段按行为与表现基线重建 |
| [maintained-project](../paths/maintained-project.md) | 正式平台、引擎与版本、语言、构建运行方式、输入设备和实际相关技术约束 | 沿用工程与表现，按具体问题局部重构 |

文件数量不证明工程可沿用。不默认选 Phaser、Web 或任一引擎；未选定正式环境不能先做任意工程再承诺低成本迁移。无真实项目时只建立适配合同，不批量制作未经运行的多引擎模板。

## 制作与迭代

1. 建立[项目入口](../templates/project-entry.md)、设计底稿及恢复点；按路径建立实际运行链。
2. 选代表性可玩切片，把规则、操作、表现与验证一起做通。按[表现协议](presentation.md)在真实构建中校准；依据体验风险试一次最可能形成无代价固定答案的反策略，例如只拖延、只堆积、只用单一角色／资源或忽略主要目标。没有对应风险时不机械枚举。
3. 扩展完整体验闭环。每个切片包含进入条件、行动与冲突规则、可感知后果、恢复／结束及验证；不能先堆全部逻辑再补反馈。实质规则变更同时扫描：预期改善、可能削弱的相邻选择／角色／阶段、失效的旧证据和下一观察点；可并入底稿，不强制另建报告。
4. 按[质量与证据](quality-and-evidence.md)检查范围、功能、理解、表现、可靠性、工程和追溯。玩家可见的胜利、评级或挑战目标先取得一条正常输入下的实际可达路径，再扩大随机／难度检查；尚未取得时如实标pending，不用边界夹具代替。修复已知 Bug，复验影响范围后才声明 V1；内部构建可随时展示，但不得用改名隐藏首次交付缺项。
5. 用户集中试玩。Agent 将观察拆成缺陷、体验问题、新需求和待判断事项，定位设计／实现／评估器的原因，修复并更新底稿与证据。
6. 用户本人认可核心玩法且其他条件满足，才可声明90+。否定玩法也可以产生有效结论；不强求每个项目无限迭代到认可。
7. 按[交付与正式开发](handoff-and-production.md)完成路径对应接收。90+、交付和发布是不同结果。

首次集中试玩反馈、核心玩法认可／否定、方向停止或路径接收后，依[反馈与学习合同](../04-agent-learning-feedback.md)完成一次里程碑学习复盘。一次性玩法Bug留在项目；确定性证据纠错可按窄范围直接修正；新的执行策略先限定试用并写`review_when`。没有方法增量时在当前验证／交付记录写`no_increment`即可，不为形式创建空学习文件。

## 按需观察、调参与复现

定义当前切片的验证办法、处理试玩反馈或反复调节时，判断观察/调节/复现/比较是否阻断任务；命中则调用可发现的 `feedback-loop`，不可发现时直接沿下方共用方法执行。明确改动或普通解释不因出现“参数”一词额外建工具。

玩法、经济、成长、AI、输入、生成、性能或表现遇到观察/复现/比较瓶颈时，按[共用反馈方法](https://github.com/ZhongTyler/AgentWorkSpace/blob/v1.14.1/meta/workspace/collaboration/support-and-learning.md#运行反馈按需观察调参与复现)处理，作为当前切片必要能力实现；不强制所有原型常驻面板或固定参数数量。共同入口不可达时，仍从待判断问题选择现有参数源、状态/日志及最小复现，必要时补预设或测试入口，并真实验证调整、生效、比较及恢复。

参数热调必须说明即时或重开生效，重置运行状态与恢复参数基线分别核查；原型实验配置不自动成为正式规格。single-file与maintained-project均可用，优先复用引擎Inspector/既有工具；隐藏信息与调试入口不进入正常玩家路径。已有冻结Demo只作历史参考，不因补方法恢复或改写。

## 设计与知识如何参与

默认沿一份底稿贯通意图、选择、规则状态、反馈、实现和证据。规则及配置以实际有效源为准，用引用连接，不从固定 EventBus／CONFIG 代码外形推断设计完整性。实现偏差先作为冲突处理，不能覆盖用户决定。

[设计模块](../design-modules/README.md)按问题加载。四层模型用于复杂依赖、责任不清或规则冲突时检查遗漏，不是强制文档树。Research 的 Weapon Farm 样本只作结构研究参考；未核实来源与许可前不复制正文或带入发布包。

Knowledge 提供资料依据，GameAnalysisDecision 提供分析和 proposed 决策包；项目授权与预算内可自主按需调用。记录来源、适用条件、冲突和不确定性，不能把检索命中当真理。重要产品决定由用户正式采用；GameAnalysisDecision 不可用时继续可独立工作，不能自动补造专家结论。调用不扩大为 Knowledge 入库、Brainstorm 回写或公开发布；反馈导出沿[反馈合同](../04-agent-learning-feedback.md)。

## 关键判断的支持信号
定义验证范围/平台、集中试玩原因不清、同类策略漏洞重复、转正式开发投入取舍时，按[共同信号](https://github.com/ZhongTyler/AgentWorkSpace/blob/main/meta/workspace/collaboration/support-and-learning.md)识别事实、知识和专业分析缺口。项目事实、Knowledge/Web案例与模型推理按适用条件互查；不把多个同源观点当独立证据。
结果直接进入底稿/验证记录：实际用了什么、怎样改变或支持选择、还缺什么。服务不可用继续独立工作；普通明确数值实现不强制研究。脱离父工作区仍沿本协议与adapter执行。
## 预算与停止扩展

有预算沿用；无依据时由 Agent 给出范围与投入估计、当前批次的有界工作及复核点，不虚构统一 Token／工时承诺，也不视为无限预算。新增费用须有对应授权。

先减少内容变体、重复工件与重复验证。相同尝试未增加证据或改善时重新诊断，再决定方法；不靠无限重试。预计不能在预算内满足承诺时，提交已完成构建、具体缺口及推荐取舍；未经决定不删减必要表现、闭环或已承诺功能。

记录可取得的用户主动投入、往返原因、实际执行及资产费用、返工和等待时间；未知就写未知。恢复只读项目入口、有效决定、当前构建、未关闭问题及必要证据，不重新读全部聊天。停止／暂停方向、有效否定结论、V1、90+ 与交付分别记录。
