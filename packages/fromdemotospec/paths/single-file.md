# single-file · 小体量验证路径

适合快速验证、正式阶段可重建的项目。与可持续路径共用[质量底线](../protocols/quality-and-evidence.md)，不能以“只是 Demo”省略关键反馈、异常行为或追溯。

## 实现前与运行

记录目标浏览器／运行器、版本要求、输入、视口和离线约束。Web 单文件交付将实际使用的脚本、样式与资源封装在一个 HTML 内；若依赖构建器，交付时保留再生成方法，运行不能隐含依赖兄弟仓、CDN或开发服务器。明确需要网络的玩法必须真实声明并验证，不伪称离线。

内部开发可以多源文件再封装，不强制全程手改一文件。输出文件名可读即可；项目放在用户指定目录或专属目录，不强制 Demo 三段式命名。存档／浏览器持久化如有需要，说明 file URL 和服务模式下的行为并实际验证。

## 职责边界

状态、规则／状态转换、输入映射和表现分工清楚。规则不从画面反推，不依赖 DOM 作为唯一真值；事件、命令、直接调用或状态订阅按复杂度选择，不要求复制固定 EventBus。

有设计意义的参数集中在可定位数据源，注明单位、有效范围及约束；不要求把无意义布局常数也升为可调参数。错误可观察、重置不留旧计时器／监听器／状态；诊断按玩法需要提供状态检查、复现场景或日志。玩家默认看到正常游戏，不被固定调试面板占据画面。

## 封装与检查

- 从最终文件启动，实际完成首次操作、完整体验循环、结束及重开；检查关键失败与连续操作。
- 封装前将内联ID及解码字节哈希与资产清单核对，拒绝缺失、额外、重复或改写的数据；再检查许可和运行时外部请求。离线资源／索引核验不证明最终HTML未变；对最终文件记录构建哈希并实际运行。资源缺失不能静默变成不可理解的图形。
- 依据风险检查焦点、尺寸变化、音频启动约束、输入与动效时序及存档行为。
- 保留可读规则、配置、表现时序与关键场景引用；自动代码扫描只能辅助查找。

交付详见[接收协议](../protocols/handoff-and-production.md)。目标引擎重建属于正式开发；迁移时传递行为和表现基线，不承诺直接沿用单文件架构。
