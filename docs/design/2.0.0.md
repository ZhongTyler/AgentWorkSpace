# AgentWorkSpace 2.0.0 设计与执行方案

基线为已公开的 1.30.0。用户已授权目标模式执行独立模块改造、创建公开子仓和发布。本文记录本轮决定、实施顺序与验收条件，实际验证范围见 [2.0.0 验证说明](../releases/2.0.0-validation.md)。

## 目标与版本

2.0.0 改变发布仓结构、模块获取与校验方式、安装器合同和模块版本管理，属于大版本升级。每个模块可独立获取、运行、发布和升级，并通过显式接口与其他模块协作。AWS 提供聚合、发现、选择、兼容审阅和组合验证。meta 提供可选的完整版协作框架。

用户可以从 AWS、任一单模块或已有工作区开始。最终安装集合由实际需要决定。Agent 读取当前任务相关入口，审阅同类工作流与替代能力后，再执行有明确授权的接入。

独立公开仓是模块发布内容的权威。AWS 通过 gitlink 引用确定提交，保持模块平级。模块间的可选协作以仓库地址、能力与接口合同声明，避免相关模块递归嵌套及重复安装。meta 同样独立发布，并保持一个完整版本。

本轮初始内容仅来自 1.30.0 已审阅公开内容。旧 _release.json 保留为迁移来源证据，新增模块发布合同负责后续版本。旧来源仓的便携导出副本转为历史迁移依据，维护入口改向新公开模块；后续内容修改在模块权威仓完成。私人研发源码、报告和项目保持原有归属。

## 模块合同

每个模块具有以下独立入口。

- README 说明用途、实际环境要求、快速开始、数据归属、验证范围，以及自己的相关模块全景。
- AGENTS 或已有领域入口规定当前用户授权、模块边界、事实归属与交付。基础入口可在没有 AWS/meta 时使用。
- module.json 声明稳定模块 ID、独立版本、仓库、入口、能力、必要运行环境、可选关系及接口版本。
- 完整文件库存与校验值保护可交付文件，保留第三方原许可与来源。
- 通用模块管理入口支持从当前模块获取相关模块，审阅现有同类能力并选择接入位置。管理工具随模块版本交付，运行时无需读取 AWS 仓。

合同使用通用字段，模块 ID 与显示名分开。版本与接口版本分开。模块自身业务代码通过配置或明确路径使用外部能力，保留无可选接线时的基础流程。发现同名目录只形成候选，实际复用依据身份、库存和工作流审阅。

## AWS 聚合与获取

AWS 源码保留首页、双语说明、模块目录、兼容合同、安装恢复工具、组合测试、发布流程和升级指南。12 个模块目录变为公开 Git submodule。普通克隆先取得聚合入口，用户再明确选择所需模块。另提供明确的全部获取操作和可选完整离线附件。

Git 历史继续保留 1.x 已公开内容，因此完整历史克隆仍可能下载历史大文件。2.0.0 的推荐入口使用轻量发布附件或浅克隆，再按需获取模块。历史 tag 与附件保持原有身份。

目录信息校验与模块文件校验分离。审计可以在未取得全部模块时完成；只有实际选中的模块需要取得并核对完整库存。获取失败保留原工作区与可恢复缓存，安装仍经过预览、冲突检测、锁与事务恢复。

当前 1.30.0 的主要压缩内容集中在 PrototypeAssets、Tools 和 Research。本轮优先改变默认下载边界，完整模块内容保持可用。素材与工具归档的进一步颗粒度拆分按实际收益评估，避免借本轮结构迁移改变工具运行行为。

## 使用路径

### 单模块

直接克隆独立仓或下载其正式附件，按本仓 README 开始。旅行、游戏项目等用户数据放包外。基础任务不要求 AWS/meta。需要相关能力时，当前模块提供关系、接口与获取入口，按审计结果安装到工作区平级目录。已经存在且经过核验的模块优先复用。

### 新 AWS 工作区

用户选择是否使用 meta，默认的新工作区方案可以推荐其完整框架。其余模块按需获取。全部模块是明确选择，不作为隐含下载。模块的独立使用入口与 AWS 中的使用入口消费同一份内容。

### 已有框架或模块

兼容审阅继续覆盖职责、输入输出、调用入口、事实与数据归属、恢复和版本。宿主已有等价能力可以满足对应要求。模块使用自己的领域合同，AWS/meta 的增强治理通过可选关系接入。现有模块与新模块的接线按用户任务决定，避免自动合并业务流程。

### 从单模块加入 AWS

识别已有模块的身份、位置、版本和修改状态。经过核验的已有实例登记为复用位置。明确的版本升级与接线改变独立预览；用户代码、Git 仓、报告、配置和原有工作流保持其自身所有权。

## 版本、兼容与发布

独立仓本轮采用 2.0.0 作为新分发合同的起点，保留 1.30.0 来源证明。后续每个模块独立使用语义版本。AWS 的版本固定一组模块提交与能力关系，并记录联合验证覆盖。未改变的模块复用其既有版本。

模块关系声明能力、协议版本、协作目的和接线条件。可选功能的具体要求在功能边界检查。例如 Knowledge 的验证后结案要求兼容 Core，基础查询可以独立运行。

README 全景由模块关系元数据生成。模块负责自身声明及其相关网络，AWS 汇总形成全景。生成器保留人工编辑的业务说明，检查元数据与图形一致性。

发布顺序为独立模块验证与提交、逐仓推送及正式版本、AWS 固定实际子提交、组合验证、AWS 提交与父仓指针、公开 tag 与附件、匿名下载和全新克隆验收。发布 tag 保持不可变。每个模块的发布包只有一份手工维护权威，ZIP 为该提交的派生产物。

## 1.30.0 迁移与恢复

1.30.0 及历史 tag、附件继续可用。既有目标工作区中的受管文件采用实际旧基线进行冲突检测，升级转换到 2.0.0 模块身份与版本记录。兼容模式保留根宿主权威。已有完整模式的 meta 根布局维持可恢复迁移，新的独立 meta 默认可作为模块接入。

独立项目副本、Knowledge 正文与历史、旅行事实、账号、工具 home、运行环境、素材与私人数据按原位置保留。模块内容和客户端 Skill 的升级仍是独立事务。用户修改过且上游需要改写的文件拒绝覆盖；上游未变的文件保留用户修改。

事务记录实际前后字节与模块身份。失败时恢复本轮修改，保留原始失败证据。逆向恢复核对之后是否产生用户修改。旧版安装器与恢复记录保持原合同，2.0.0 恢复入口明确支持本轮新记录和 1.30.0 迁移事务。

## 实施顺序与门

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| 1. 基线与方案 | owner/index 基线、独立工作区、本文、仓库名称和授权核对 | 已公开来源明确，写范围和恢复边界可核查 |
| 2. 通用合同与样板 | 模块身份、相关关系、独立管理入口、Travel 样板 | 新目录无 AWS/meta 可用，相关模块获取及冲突保护通过 |
| 3. 全模块改造 | 12 个独立仓内容、入口、许可与局部全景 | 逐模块库存和独立使用合同通过 |
| 4. AWS 聚合 | submodule、按需获取、目录校验、全景、升级恢复 | 部分模块缺席时审计可用，选取及全部获取按实际选择工作 |
| 5. 验证 | 当前矩阵、1.30.0 迁移、相关安装、复用、失败与回退 | 实际退出码通过，未覆盖的体验与在线能力清楚记录 |
| 6. 公开发布 | 模块与 AWS tag/Release/附件、父仓闭合 | 远端身份、匿名附件、全新独立和聚合工作区验证通过 |
| 7. 收尾 | 来源维护入口迁移、工作区父边、恢复备份、任务资源清理 | 所有已授权必要阶段有真实结果，其他 owner 状态保持 |

## 验收矩阵

- AWS 普通克隆不获取模块正文；选择一个模块只获取该模块及明确同意的必要依赖。
- 全部模块获取有显式入口，读取的是各独立仓实际发布提交。
- 12 个模块分别通过库存和独立入口检查，读取范围不依赖原作者目录或 AWS 的父目录。
- Travel 在无 meta/AWS 的陌生目录完成虚构旅行的创建、构建与校验。
- 单模块可以审阅并获取相关模块，已有同模块实例按经验证身份复用，已有同类工作流形成兼容审查项。
- 未安装 AWS/meta 的 Research、Knowledge、Skills、游戏等基础使用路径按实际运行环境分别验证。
- 模块局部图与 AWS 全景来自同一模块关系声明，链接、能力和版本约束一致。
- 真实 1.30.0 全部/兼容工作区升级保留私人 canary、宿主权威、独立项目副本及客户端 Skill 选择；冲突拒绝与逆向恢复可核对。
- 获取、安装中断和并发锁不遗留被误认为完整的安装；链接/越界路径与未审阅覆盖被拒绝。
- 所有公开仓与固定 gitlink 可匿名获取，正式附件校验值一致；独立模块和 AWS 的全新公开副本分别验收。

工程测试、合成输入和浏览器渲染证据各自注明范围。真实研究质量、游戏体验、艺术质量、在线服务及长期使用收益沿实际任务验收。

## 投入与恢复

复用 1.30.0 的原文件事务、兼容审阅、来源与许可证据和未改变的运行测试。新测试集中覆盖新分发边界与迁移回归。每阶段核对有效增量、实际耗时和剩余门；模型 token/费用无可靠读数时记 unknown。外部付费或模型调用为零。

同一失败签名连续两轮失败时停止该修复路线并交用户决定。公开仓创建和 Release POST 保留请求结果及远端读回，未知结果先查实际对象再决定重试。已公开 tag 不改写。既有主干分歧与无关 dirty/index 保留，来源与直接父仓结果分别核验。
